# aip-integration-streaming-056: 流式推理与响应式客户端

## Concepts

### 1. Streaming 与非流式响应

非流式调用通常等待模型生成完整结果后，再将答案返回。

流式调用允许应用逐步接收生成结果，并在生成结束前向用户展示部分内容。

教学示例：

| 方式 | 用户看到第一段文字 | 用户看到完整答案 |
|---|---:|---:|
| 非流式 | 约第 8 秒 | 约第 8 秒 |
| 端到端流式 | 约第 1 秒 | 约第 8 秒 |

以上数字仅用于说明机制。

流式可以改善等待体验，但不保证模型更早生成完整答案。

### 2. TTFT 与总完成耗时

TTFT（Time to First Token）关注首个 Token 出现前的等待时间，总完成耗时关注整个响应何时结束。

测量时必须明确观察位置：

- 模型开始输出。
- 后端收到第一段文本。
- 浏览器收到第一段文本。
- 页面首次显示文字。

这些时间点不同，不能混用。

对 Agent 而言，前面的检索、工具调用和研究过程也会增加用户等待时间。Synthesizer 的流式生成不能消除这些上游等待，可以另行展示真实任务进度。

### 3. 端到端流式链路

完整链路是：

模型输出事件 → Node.js 增量读取 → 后端增量转发 → 浏览器增量接收 → UI 更新。

任意一层等待完整结果，都可能让用户直到最后才看到答案。

教学反例：

```ts
let answer = "";

for await (const chunk of modelStream) {
  answer += chunk.text;
}

res.json({ answer });
```

这段示意代码在后端读取完整结果后才返回。模型到后端是流式，后端到浏览器却不是。

因此，调用流式模型 API，不等于已经实现端到端流式体验。

### 4. Bedrock 流式 API

| API | 主要特点 |
|---|---|
| ConverseStream | 使用统一消息接口接收流式响应 |
| InvokeModelWithResponseStream | 使用对应模型的请求与响应格式调用流式推理 |

调用前需要确认具体模型支持流式响应。

ConverseStream 的输出包含不同类型的事件，例如：

- 消息开始。
- 内容块增量。
- 内容块结束。
- 消息停止。
- 元数据。
- 错误。

不能把所有事件都当作正文拼接。应用应识别事件类型，再分别处理文本、控制信息和错误。

### 5. 增量片段与应用事件

一个文本片段不保证对应完整词语或句子，不能依赖片段边界判断业务含义。

生成 JSON 或工具参数时，也不能把未完成片段直接当作完整对象执行。

后端可以将模型事件转换为应用自己的事件格式，例如：

```ts
type AppEvent =
  | { type: "text_delta"; text: string }
  | { type: "done" }
  | { type: "error"; message: string };
```

这属于本次讨论中的教学设计，不是 AWS 原始事件定义。

应用应根据实际结束原因判断是否生成成功，不能简单把任何消息停止都转换成业务完成。

### 6. 后端到浏览器的传输与渲染

可以根据交互需要选择 SSE、通过 fetch 读取流式响应，或 WebSocket。

单次提问后持续接收结果的场景，可以使用 HTTP 流式响应。

模型服务的事件流与浏览器 SSE 属于不同协议层，后端需要解析和转换。

需要检查：

- 后端是否及时写出片段。
- 代理、网关或压缩层是否缓冲响应。
- 浏览器是否增量读取，而不是等待完整响应。
- UI 是否及时更新，而不是只累积数据。

前端不必收到每个极小片段都立即渲染。可以短暂合并更新，降低渲染开销，同时保持及时反馈。

### 7. 完成、失败与取消

输出了部分文本，不代表业务成功完成。

| 状态 | 含义 |
|---|---|
| Streaming | 正在接收结果 |
| Completed | 已确认正常完成 |
| Failed | 出现错误，可能已有部分内容 |
| Cancelled | 用户取消 |

例如页面显示“我推荐产品 A，因为它……”后连接断开，这只能视为部分结果，不能标记为完整回答。

需要结合消息结束原因判断：

- 正常结束。
- 达到输出长度限制。
- 等待工具调用。
- 流式错误。

连接关闭本身不足以证明成功。

### 8. 重试与取消的边界

失败后重新生成，不能直接把新答案拼到旧片段后面，否则可能出现重复或语义不连贯。

Agent 的生成重试还需要与工具执行重试区分，避免重复执行已有副作用的动作。

用户点击停止时，应用应尽可能把取消传递到上游，而不只是停止页面渲染。上游是否已经停止计算，应根据具体服务的实际行为确认。

### 9. 流式排障与时间点观测

可以记录：

1. 后端收到用户请求。
2. 后端收到模型第一段文本。
3. 后端转发第一段文本。
4. 浏览器收到第一段文本。
5. 页面首次显示文字。
6. 响应最终完成。

教学场景：后端第 1 秒收到模型文字，页面第 8 秒才显示完整答案。

优先检查后端是否实时转发：

- 第 8 秒才第一次写出：调查后端是否等待完整答案。
- 第 1 秒已写出：继续调查代理缓冲、浏览器读取与页面渲染。

后端调用写出方法的时间，是定位依据之一，不等于浏览器已经收到数据。

## Concept Relationships

### 模型流式与客户端流式

模型流式解决后端何时获得增量内容；客户端流式解决用户何时看到这些内容。

两者需要通过增量转发连接，才能改善端到端体验。

### 事件解析与业务完成

文本增量用于展示，控制事件和结束原因用于判断执行状态。部分文本、消息结束和业务成功不能直接画等号。

### TTFT 与链路可观测性

分阶段记录时间点，才能区分模型启动、后端缓冲、网络传输和前端渲染延迟。

仅观察总响应耗时，无法确定首段文字在哪一层被延迟。

### 与已有工程经验的联系

流式文本展示与高频实时 UI 都需要平衡更新及时性和渲染成本，可以通过合并更新减少频繁渲染。

生成重试与工具执行重试需要区分，连接到 Agent 幂等性和副作用控制。

## Understanding

在“后端第 1 秒收到文字、页面第 8 秒才完整显示”的场景中，用户提出检查：

> 有没有流式输出。

该回答识别了应先检查后端到浏览器是否真正流式传输。

讨论进一步明确：

- 检查后端第一次写出数据的时间。
- 后端及时写出后，再检查代理缓冲、浏览器增量读取和 UI 更新。
- 模型到后端、后端到浏览器是需要分别确认的链路。

用户确认了这一解释。本次未进行真实代码改造、缓冲定位、取消传播或中断恢复测试，不据此认定已具备独立实操能力。
