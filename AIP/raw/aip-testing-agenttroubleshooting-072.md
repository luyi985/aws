# aip-testing-agenttroubleshooting-072: Agent 评估与故障定位

## Concepts

### 1. 评估发现问题，Trace 帮助定位原因

Agent 评估先判断是否完成用户目标，再沿执行链定位失败原因。不能因为最终回答错误，就直接认定模型能力不足。

以产品选购助手为例，用户要求：

> 在澳洲购买某型号产品，总价不超过 300 澳元，并且有本地库存。

成功需要同时满足：型号正确、总价符合预算、库存符合要求，以及回答有实际查询结果支持。

排查时沿着以下链路检查：

**用户目标 → 规划 → 工具选择 → 参数传递 → 权限检查 → 工具执行 → 结果综合。**

重点是找到数据或行为**第一次出错的位置**。Trace 提供调用和结果证据，但仍需要结合执行器日志、工具日志及实际模型输入判断。

### 2. 规划失败：遗漏步骤或错误安排依赖

规划失败包括遗漏必要步骤、没有澄清关键信息，或没有处理任务依赖。

例如：

- 型号不明确，却直接搜索并推荐。
- 只比较商品价格，没有计算运费。
- 尚未确定产品型号，就查询某个具体型号的库存。

即使系统没有显式输出 Plan JSON，模型在工具调用循环中仍然需要决定下一步。因此，没有独立 Planner，也可能发生规划错误。

排查应检查实际用户输入、已有 state、可用工具和缺失信息，判断必要步骤是否被遗漏。

### 3. 工具选择：先确认工具是否实际可用

工具选错前，应先检查正确工具是否被注册、启用，并实际提供给本次模型调用。

如果正确工具根本没有进入模型输入，属于配置或工具暴露问题；如果工具已经提供，再检查名称、描述和能力边界是否清楚，是否与其他工具重叠。

例如，查询实时库存应使用库存工具。产品介绍检索工具即使返回相关文本，也不一定能证明当前有货。

### 4. 参数错误：区分模型生成与执行器传递

工具参数需要检查两个层面：

- **结构正确性**：必填字段、类型和格式是否符合 schema。
- **语义正确性**：参数是否指向用户真正要求的产品或资源。

符合 schema，并不代表业务含义正确。`productId` 是合法字符串，也可能选错产品。

应对照：

**模型生成的参数 → 执行器映射后的参数 → 工具实际收到的参数。**

本次讨论的例子：

```text
模型生成：productId = A
执行器传递：productId = B
工具返回：产品 B 的结果
```

这里错误首次出现在执行器。应优先检查字段映射、旧 state、默认值覆盖等问题。工具根据 B 返回 B 的结果，本身可能完全正常。

### 5. 权限问题：找到失败的具体调用环节

工具调用可能经过多层，例如 Agent 调用 Lambda，Lambda 再访问数据库。

出现拒绝访问时，需要确认：

- 哪个身份发起调用。
- 请求什么操作、访问哪个资源。
- 哪一层拒绝了请求。

IAM 权限与业务授权也需要区分。服务角色可以读取数据库，不代表当前用户有权查看数据库中的任意任务或文档。

权限不足通常不能靠重试解决。应补齐所需的最小权限，或修正业务授权判断。

### 6. 工具执行失败：区分错误类型再处理

| 现象 | 优先调查方向 |
|---|---|
| 429 / 限流 | 调用频率、并发和退避策略 |
| 超时 | 网络、下游耗时和超时配置 |
| 5xx | 工具服务或下游故障 |
| 请求成功但数据错误 | 参数、数据源和业务逻辑 |

重试适用于部分暂时性失败，但不应无条件重试。对于创建订单等有副作用的操作，还需要幂等机制，避免同一操作重复执行。

### 7. 结果综合：检查模型实际收到的 Context

假设工具正确返回：

```json
{
  "totalPriceAud": 280,
  "localStock": false
}
```

最终回答却说“总价 280 澳元，有本地库存”。

应先检查最终模型输入：工具结果是否进入 Context，是否被截断，以及是否混入旧结果、无关内容或冲突信息。

只有确认模型收到完整、正确的结果后，才进一步调查提示词、指令冲突和模型生成行为。

同时要区分不同质量问题：

- 工具说无货，回答说有货：缺乏忠实性。
- 回答准确报告价格 450 澳元，却推荐给预算 300 澳元的用户：违反用户约束，不一定属于忠实性问题。

### 8. 用隔离实验验证根因

可以通过缩小执行范围来定位问题：

- 用确认正确的参数直接调用工具，检查工具行为。
- 将确认正确的工具结果直接提供给综合模型，检查最终回答。
- 缩减工具和 Context，观察错误是否仍然出现。

修复后，应重跑原失败案例及相关回归案例，并记录模型、提示词、工具 schema 和数据版本，避免把偶然成功当作修复完成。

对于 Bedrock Agents Classic，还要检查修改是否经过 Prepare，以及实际调用的版本和 alias 是否正确。

### 9. Agents Classic 的替代方向

本次查阅的 AWS 文档推荐迁移至 **Amazon Bedrock AgentCore**，提供两条路径：

- **Managed agent harness**：配置模型、工具和指令，由服务托管 Agent 循环。
- **Code-defined agents**：自行编写 Agent 逻辑，部署到 AgentCore 的托管环境。

Classic 的 Action Groups 可映射为 Gateway 暴露的工具或代码工具；Knowledge Bases 可通过 Gateway 或检索工具接入。

这改变了具体配置与部署方式，但沿调用链定位规划、参数、权限、执行和综合错误的方法仍然适用。

## Concept Relationships

- **规划决定需要做什么，工具选择决定使用哪个能力，参数决定具体操作哪个对象。** 三层都可能导致查错产品，但修复位置不同。
- **执行器连接模型与工具。** 模型参数正确，不保证执行器传递正确，因此必须检查边界两侧的数据。
- **工具成功不等于任务成功。** 还需要确认数据进入最终 Context，并被正确用于回答和满足用户约束。
- **评估与 Trace 共同支持修复闭环。** 评估发现失败，Trace 和日志支持定位，隔离实验验证根因，回归评估检查修复效果。

## Understanding

用户在参数映射案例中明确指出：

> 应该看执行器，查看为什么参数错误地传入工具。

这说明在该案例中，用户能够根据模型输出与实际工具输入之间的差异，将调查重点放在执行器，而不是直接修改模型提示词。
