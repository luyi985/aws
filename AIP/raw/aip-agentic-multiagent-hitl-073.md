# aip-agentic-multiagent-hitl-073: Multi-agent Workflow 与 Human-in-the-Loop

## Concepts

### 1. Orchestrator、Worker 与 Synthesizer

Multi-agent Workflow 将复杂任务分配给职责不同的 Agent，再协调它们的执行与结果。

| 角色 | 核心职责 | 产品研究教学案例 |
|---|---|---|
| Orchestrator | 拆解目标、分派任务、检查缺项、决定下一步 | 安排价格、保修与评价调查 |
| Worker | 在任务边界内选择动作、调用工具并返回结果 | 搜索多个商家，核对型号和价格 |
| Synthesizer | 综合证据、识别差异、生成最终回答 | 根据需求和预算形成推荐 |

这些是逻辑职责，不要求必须部署成三个独立 Agent。Orchestrator 也可以承担 Synthesizer 的工作。

Worker 返回结果时，应包含必要的证据、适用条件和未确认事项，而不只是一个结论，否则下游难以验证或综合。

### 2. Worker Agent 与普通工具

普通工具通常执行明确的操作，例如：

`getPrice(productId)` → 返回产品价格。

Worker Agent 则可以在任务边界内决定下一步：

1. 搜索产品。
2. 发现结果混入其他型号。
3. 调整搜索条件。
4. 比较多个商家。
5. 返回价格、来源和未确认事项。

关键区别是 Worker 拥有一定的行动选择能力。如果任务只是执行一次固定查询，普通工具可能已经足够。

多 Agent 会增加模型调用、交接和协调成本。多个 Agent 也可能共享同一种错误认识，因此一致意见不能替代事实验证。

### 3. Sequential 与 Parallel

执行顺序应根据数据依赖确定。

**Sequential：串行执行**

后一步需要前一步的结果，例如：

准确型号确认 → 查询该型号价格 → 计算含运费总价。

型号未确定时，后面的价格查询可能针对错误产品。

**Parallel：并行执行**

任务可以根据现有输入独立完成。例如准确型号确定后，可以同时调查：

- 价格。
- 保修政策。
- 用户评价。

实际流程可以组合两者：

先串行确认输入，再并行调查，最后综合结果。

这与普通服务判断哪些请求可以并发执行具有相同的数据依赖基础；Agent 的任务拆解与执行路径还可能由模型动态决定。

### 4. 共享输入与任务交接

协调者应提供明确、统一的任务输入，例如品牌、准确型号、地区和用户限制。

如果型号未明确，可能出现两类失败：

| 情况 | 表现 |
|---|---|
| 明确报告信息不足 | Worker 返回需要补充输入 |
| 隐性输入不一致 | 不同 Worker 各自猜测型号，结果无法合并 |

例如，价格 Worker 查询基础版，保修 Worker 查询 Pro 版，评价 Worker 查询上一代。每个任务都可能执行成功，但综合结果无效。

因此，Worker 应返回自己实际使用的型号和条件，便于协调者检查一致性。

缺少必要输入时，可以使用 `needs_input` 等业务状态，与工具超时等执行错误区分。协调者收集缺失项后统一询问用户，避免多个 Worker 重复提问。

### 5. HITL 与人工升级条件

Human-in-the-Loop 允许人在执行过程中补充信息、纠正方向、审批动作或接管任务。

| 触发条件 | 人工介入方式 |
|---|---|
| 需求或输入不明确 | 补充关键信息 |
| 可信来源相互冲突 | 核验或判断冲突 |
| 多次执行失败、无法继续 | 人工接管 |
| 涉及受控操作 | 指定人员审批具体动作 |

升级条件不应只依赖模型自报的置信度。可以结合可观察信号，例如关键证据缺失、来源冲突、校验失败或重试次数超限。

人工批准也不能替代权限验证：系统仍需判断审批者是否有权批准对应操作。

### 6. Clarification 与 Approval

| 类型 | 解决的问题 | 人提供的内容 |
|---|---|---|
| Clarification：澄清 | 任务条件是什么？ | 缺失信息、限制或偏好 |
| Approval：审批 | 具体动作能否执行？ | 对明确动作的批准或拒绝 |

用户补充产品型号，不等于批准购买。

流程应记录暂停原因、缺失信息和恢复位置。用户回复后，更新共享状态，再恢复相关步骤。

对于审批，应展示具体动作及参数。例如批准“向商家 X 购买产品 A，总价 $180”，而不是笼统批准“继续购物”。

### 7. 多个审批点如何区分

不能只依赖聊天中的一句“同意”判断批准对象。

每次审批请求都应有独立标识，并关联工作流实例、暂停位置和具体动作。以下是本次讨论中的通用工程设计示例，不是某个框架规定的字段格式。

| approval_id | workflow_run_id | checkpoint_id | 待审批动作 | 状态 |
|---|---|---|---|---|
| AP-101 | RUN-001 | buy_product | 购买产品 A，总价 $180 | pending |
| AP-102 | RUN-001 | send_report | 向指定收件人发送报告 | pending |

用户针对某条记录提交决定：

```json
{
  "approval_id": "AP-101",
  "decision": "approve"
}
```

后端根据审批 ID 找到对应记录，校验审批人权限、动作参数和当前状态，再更新审批状态并恢复对应步骤。

不能只使用检查点名称：同一步骤可能在循环中多次执行，也可能在不同工作流实例中同时等待审批。每次审批请求需要独立 ID。

如果同时存在多个待审批项，应要求用户明确选择，或使用绑定审批 ID 的按钮，避免由模型猜测“同意”指向哪个动作。

### 8. 审批版本、重复处理与恢复

批准应绑定具体动作版本。用户批准总价 $180 后，如果实际动作变为 $250，旧批准不能直接复用，应重新审批。

审批状态可以通过原子条件更新，避免同一条待审批记录被重复接受。与此同时，“审批只接受一次”和“业务动作只执行一次”是不同的问题：实际执行仍需保留防止重复操作的控制。

Checkpoint 与 Approval 也不是同一概念：

- Checkpoint 保存执行状态或暂停位置。
- Approval 表示等待人决定的请求。

两者需要关联，但不一定一一对应。同一个状态快照中可以包含多个待审批请求。

本次建立的执行流程是：

创建审批请求 → 保存暂停状态 → 用户针对审批 ID 决策 → 校验权限与动作版本 → 更新审批状态 → 恢复对应步骤。

### 9. User Feedback Loop

用户反馈应改变后续执行依据。

例如用户说“不要海外商家，只看澳洲本地库存”，协调者应把限制写入当前任务状态，让相关 Worker 按新条件重新调查，再生成推荐。

这属于执行过程中的反馈回路，不意味着模型参数自动更新，也不代表系统永久记住了该偏好。

### 10. AWS 服务映射与版本说明

本次读取的 Bedrock 多 Agent 官方文档采用 Supervisor 与 Collaborator 模式：

- Supervisor 协调任务并进行分派。
- Collaborator 负责特定领域。
- 各角色应明确职责，减少职责重叠。

针对特定 Action Group 操作，可以启用用户确认，让用户批准或拒绝执行。这是 HITL 的一种实现，不能代表所有人工升级流程。

本次读取时，官方文档注明原 Bedrock Agents 已称为 Agents Classic，不再向新客户开放，现有客户可继续使用，并引导新客户了解 AgentCore。该说明是本次读取到的服务状态，不改变本 KP 的通用工作流概念。

## Concept Relationships

### 任务依赖决定执行方式

Orchestrator 根据任务依赖决定串行或并行。Worker 根据统一输入执行，Synthesizer 根据可比较的结果综合答案。

缺少共享输入时，并行可能放大输入不一致问题，因此应先确认必要条件。

### HITL 与任务状态连接

HITL 不是独立于工作流的一段聊天。人的补充或决定必须与当前任务状态关联，才能恢复正确步骤。

澄清更新任务条件；审批改变具体动作的执行许可。两者不能互相替代。

### 审批 ID 与 Checkpoint 连接

审批 ID 标识一次具体的人类决策请求，Checkpoint 保存执行状态。通过两者关联，系统才能区分多个待审批动作并恢复对应执行。

### 反馈形成执行闭环

执行结果或人工反馈可以让协调者调整任务、补充信息、重新分派或停止执行，而不是始终按照最初计划推进。

## Understanding

用户对型号未明确的场景提出：

> 三个 Worker 可能因为缺少必要信息而停止工作，返回错误状态，要求主 Agent 询问用户提供信息。

这表明用户能识别必要输入缺失，并提出由 Worker 向协调者反馈、再由协调者向用户澄清的处理路径。

讨论进一步补充：

- 信息不足可以单独表示为 `needs_input`。
- 不应让多个 Worker 各自猜测型号。
- 协调者统一澄清，并维护共享输入。

用户随后询问：

> 如果多个 Checkpoint 需要 HITL，怎么区分用户批准了哪个 Checkpoint？

讨论由此展开了独立审批 ID、工作流实例、暂停位置、动作版本，以及审批后恢复执行的关联机制。用户表示理解；本次未进行独立实现或重复执行故障验证。
